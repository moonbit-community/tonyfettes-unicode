MoonBit Unicode performance

How fast the MoonBit Unicode library normalizes, segments, resolves bidi, converts domain names and maps case: on every merge to main, and against ICU4X, ICU4C and, on the JS backend, JavaScript's own built-ins. Lower times are better.

Every merge to main

Changes on main

For every merge, CI builds the MoonBit harness at the merge and at its first parent, runs the two in turns on the same GitHub runner and keeps the fastest round of each case. Each cell is the change in time, the geometric mean over the operation's inputs: green is faster, red is slower. Runners are shared machines, so changes within the run's noise, shown in grey, mean nothing.

Tick a merge, then another, to combine the run of merges from one to the other: the combined row is the change from before the oldest to after the newest, chained input by input from each merge's own comparison. Their noise adds up, so a combined change has to be larger than a single one to leave the grey. The address keeps the range, to link to.

Native and Wasm

Against ICU4X and ICU4C

Geometric mean over each operation's inputs. MoonBit, ICU4C and ICU4X's UTF-16 API all work on UTF-16, and only libraries that take UTF-16 are shown, so every bar reads the same bytes. ICU4C is used through UnicodeString, ICU4X through its _utf16 APIs. The verdict under each chart compares MoonBit native with the fastest of the others. MoonBit runs on two WebAssembly backends: wasm-gc, whose objects V8's garbage collector manages, and wasm, which keeps everything in linear memory with reference counting.

JavaScript backend

MoonBit compiled to JS vs the built-ins

JavaScript does have built-ins for some of this. String.prototype.normalize and Intl.Segmenter are implemented in C++ inside V8, on top of ICU4C. Node also ships url.domainToASCII (the ada URL parser) and the deprecated punycode module, which is plain JS. There is no built-in for bidi resolution or an NFC check, so those have no JS counterpart here.

So this pits MoonBit compiled to JavaScript against native ICU code reached through V8. Every Node case pays the cost of crossing from JavaScript into the runtime, and domainToASCII converts the string to UTF-8 inside it. domainToUnicode first runs the whole ToASCII conversion and then decodes the result back, so it always costs more than ToASCII.

Operation
Method and caveats

Protocol. Every harness reads the same input files, doubles the iteration count until one sample takes at least 5 ms, and keeps the fastest of 5 samples, counting that one. Each cell is the fastest of several rounds, which run one harness at a time. File I/O and input preparation are outside the timed calls. Every result is kept where it can be read later, so that no optimizer can drop the work that builds it.

Changes on main. Both commits run the harness of the merge, so a change to the harness does not show up as a change to the library. They take turns going first in each round. The noise of a run is the median over its cases of slowest round / fastest round; a change no larger than that is greyed out.

Combined merges. Each merge is compared on its own runner, and the runners differ in speed, so times are never compared across merges, only each merge's ratio of head to base. Per input, the ratios of the merges multiply into the change over the range, and the geometric mean over the inputs that every merge measured gives the operation's. Inputs added within the range are left out. The noise is the merges' noises added in log space as a root sum of squares. For a figure measured in one go, run bench/xlang -- --base <older commit>.

Inputs. Normalization uses the 14 ICU normperf corpora, as they are and converted to NFD. NFD → NFC composes the decomposed copy, forcing real work. Most corpora are already NFC, so MoonBit, ICU4X and Node can return the input unchanged on NFC, NFKC and the NFC check.

Encodings. Every implementation shown in the snapshot takes UTF-16: MoonBit's String, ICU4C's UnicodeString, ICU4X's _utf16 APIs, unicode-bidi's UTF-16 module and JavaScript strings. The harness also measures Rust libraries that read UTF-8. They are left out here: UTF-8 makes ASCII cheaper and CJK dearer, so those numbers mix the encoding with the algorithm.

Builds. MoonBit native is compiled through C with clang. Wasm-gc and wasm run in V8 under moonrun. The JS backend runs under Node. The Rust harness is a release build (fat LTO, one codegen unit) with ICU4X's compiled data.

Case and categories. The harness feeds ICU4X and Rust's std these per-character lookups from UTF-8 strings, so the snapshot compares them with ICU4C only. Full uppercase mapping has no UTF-16 peer and is not shown there.

Wasm and wasm-gc. The wasm backend shares the native backend's SIMD path, so it beats wasm-gc on NFC, NFKC and the NFC check, where the clean-text scan dominates. Elsewhere it is usually slower: it reference-counts and allocates with MoonBit's own allocator inside linear memory, while wasm-gc allocates from V8's collector. Results also depend on what ran earlier in the same process, as V8's heap grows, so both the snapshot and the changes on main come from runs of the full suite.

Source: bench/xlang. Run moon run --target native bench/xlang for the snapshot, moon run --target native bench/xlang -- --base HEAD^ for the changes of one commit. See bench/xlang/README.md.
